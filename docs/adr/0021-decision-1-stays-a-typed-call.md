# ADR-0021 — Decision-1 stays a typed call; transparency comes from a pinned protocol and a ledger, not an agent wrapper

Status: accepted by the owner's delegate, 2026-10-11, on the recommendation of a `claude-opus-5.5` oracle
review. Records a decision **not** to change the decision-model call path. It supersedes no ADR; it extends
[ADR-0018](0018-microsoft-decision-1-replaces-the-vendor-classifier.md) (one model, both roles) and
[ADR-0011](0011-ai-architecture-layers.md) (three layers, deterministic core in authority) by saying what
the decision layer is *made of*.

## Context

The owner asked whether the decision model should be served through a **custom agent in Foundry**, on the
grounds that it would make the process more transparent.

The proposal was examined against the three ways Microsoft Foundry offers to run an agent, and against what
is already auditable here.

**What "a custom agent for the decision model" would mean mechanically.**

- A **prompt agent** is a versioned instruction set bound to a Foundry model deployment and invoked with
  `agent_reference` — which is exactly how narration already works (`luvn-narration:8`, ADR-0018's sibling
  decision). Decision-1 is not reached that way: it answers the typed `systemone` protocol at
  `/providers/microsoft/v1/systemone`, with a `state` and `questions` request and an `answers` object back.
  Binding it to a prompt agent is not a configuration change; it is a different protocol.
- A **hosted agent** is our own container running in Agent Service. It would make the same `httpx` POST, so
  the call would move without changing — the same protocol, one more runtime, identity and failure mode to
  own.
- A **connected-agent** or multi-agent setup puts a model in the control flow, deciding when to call the
  classifier. That conflicts directly with [ADR-0011](0011-ai-architecture-layers.md): the deterministic
  core is the sole authority, and permission is decided before any model sees a record.

**What the change would cost.** Today each candidate record has a chain that can be audited at every link:
a typed question → an `answers` object with per-option probabilities → a deterministic gate
(`ADDITION_FLOOR = 0.60`, `OMISSION_FLOOR = 0.70`, `DECISION_MARGIN = 0.25`) → a recorded outcome. Wrapping
that in an agent inserts natural-language instructions that drift between versions, an intermediate free-text
step, and a response shape that does not carry the calibrated per-option probabilities in the same form. The
run becomes *visible in a portal* and *less inspectable as evidence*. Being visible is not the same property
as being transparent, and ADR-0018 already shows how much this repository depends on those probabilities:
the threshold sweep, the floor ablation and the subject-binding margin are all read off them.

**What is genuinely missing.** Not the protocol — the protocol is better than an agent's. What is missing is
that the protocol is not *pinned as a value* anywhere a reviewer can compare, and that there is no
distributed trace joining the layers. The repository is explicit about the second: App Insights holds
scrubbed app-side stage events, not Foundry service-side spans.

## Decision

1. **Decision-1 remains a typed call.** No prompt agent, no hosted agent, no connected-agent orchestrator
   stands between the application and `/providers/microsoft/v1/systemone`. An agent may write prose; an agent
   never decides relevance, and never decides permission. The narration side keeps its versioned prompt agent,
   because prose is the one thing an agent is the right tool for.

2. **The protocol becomes a pinned value.** `backend/app/decision_protocol.py` describes the roles, the
   `state` fields, every question with its wire type and answer vocabulary, and the gates applied to the
   answers. The descriptor's canonical JSON has a SHA-256 literal, and
   `backend/tests/test_decision_protocol.py` fails until the literal and the descriptor agree — so a question
   added, changed or dropped is caught in review rather than discovered in a later measurement. The rendering
   a human reads is [`docs/decision-protocol.md`](../decision-protocol.md), generated by
   `backend/scripts/render_decision_protocol.py`.

   **What the pin covers, stated precisely, because an overclaim here would be the same defect this record
   exists to prevent.** The digest is over the *structural descriptor*: roles, state keys, question names,
   wire types, answer vocabularies and the gate identifiers. It does **not** cover the full Finnish
   `instructions` and criteria strings, and it does **not** cover the numeric gate values
   (`ADDITION_FLOOR`, `OMISSION_FLOOR`, `DECISION_MARGIN`). The selection test compares state keys, question
   keys and types; the verifier test checks its descriptor shape, not the verifier's assembled request. So
   this is a **partial structural pin**: it makes a change to the protocol's *shape* impossible to land
   silently, and it leaves the wording and the thresholds to review. An earlier revision of this ADR read as
   though the effective behaviour were pinned; an oracle review on 2026-10-11 established that it is not, and
   the distinction matters most in the comparison below — an independently editable agent prompt would put
   even the wording outside this pin, which is the argument's direction, not a claim that the wording is
   already inside it.

3. **The per-record outcome stays in the `Picture` and is what a ledger would carry.** The response already
   publishes, for every assessed record, the Decision-1 `status`, the probabilities and the rule version, and
   the UI renders them in the audit trail. This ADR does not add a second store of the same facts: it records
   that the existing surface *is* the ledger, and that a future out-of-band ledger must not become a second
   source of truth for a number the `Picture` already owns.

4. **Distributed tracing is the accepted next step, and it is not claimed yet.** The recommendation is to
   instrument both model layers with OpenTelemetry into the project's Application Insights so one trace joins
   the permission cut, the Decision-1 spans, the narration agent run, and the per-sentence verifier. Until
   that exists and has been captured, the documents keep saying what they say today — app-side custom events,
   no service-side spans — and this ADR is the record of the gap rather than a claim that it is closed.

5. **A Foundry Agent Service batch evaluation of `luvn-narration:8` is worth running once, and it is not
   clinical evidence.** It would prove that the *deployed, versioned* agent behaves as the local prompt copy
   does, give a reproducible run recorded against version 8, and provide a regression baseline for `:9`. It
   cannot prove clinical correctness (its evaluators are LLM judges), it overlaps the repository's own
   verifier so agreement between them is not independent, and it says nothing about Decision-1 relevance or
   the permission cut. The top open evidence gap remains an independently clinician-labelled, blinded
   sentence-and-citation benchmark.

## Consequences

- The auditable surface is the protocol and the probabilities, not a portal view. A reader can inspect
  `docs/decision-protocol.md` and the response, and reproduce the gates.
- Changing a question is now a two-file change with a gate that refuses to let them disagree. That is
  deliberate friction on the one interface whose silent drift would invalidate every measurement in
  `.scratch/`.
- The transparency goal is met *partially and honestly*: the protocol is pinned and published; tracing is
  named as the remaining work rather than described as present.
- No second identity, no second runtime and no second failure mode is introduced on the decision path.

## What this ADR explicitly does not authorise

- Moving Decision-1 behind any agent type, or letting an agent call permission or relevance as a tool.
- A `LUVN_DECISION_AGENT`-style switch: a setting that can only misconfigure the single-model choice is the
  shape ADR-0018 already removed once.
- Presenting a batch-evaluation score, or a portal trace, as clinical validation or as grounding proof.
- Emitting record ids, note text or prompts into spans when tracing is added; the GenAI conventions record
  prompts by default and that has to be turned off.

## What would change this decision, and one capability fact that shapes it

An oracle re-examined this decision on 2026-10-11 at the owner's request and **upheld it**, with one
capability fact worth recording because it is the thing that makes "just wrap it in an agent" unsound rather
than merely unnecessary:

- **Provider-enforced structured output is not available to agent-wrapped calls.** Microsoft documents
  JSON-Schema structured outputs for *direct* Chat Completions / Responses calls and lists the Foundry Agent
  Service as **unsupported** for that feature
  ([structured outputs](https://learn.microsoft.com/en-us/azure/foundry/openai/how-to/structured-outputs)).
  That is already visible in this repository: the narration path receives JSON **text** from the versioned
  agent and validates it application-side with Pydantic (`backend/app/llm.py`), while the direct typed calls
  get a schema the provider enforces. So an agent wrapper could not reproduce the native
  `state`/`questions` → `answers` contract with calibrated per-option probabilities by asking a chat model for
  JSON; a **hosted pass-through** could return the native response unchanged, but then it is the same
  `httpx` POST with one more runtime, identity and failure mode, and no better decision.

- **The decision flips only on a demonstrated, non-cosmetic requirement** — a concrete Foundry-level control
  that cannot be had from a direct call — *and* only if a shadow benchmark shows: the native
  `state`/`questions` → `answers`/probabilities contract byte- or semantically unchanged; the same
  Data-Zone processing; a bounded fan-out whose p95/p99 latency and failure rate are no worse; an immutable
  version plus the protocol hash; and no tools and no conversation history. Agent packaging alone is not that
  requirement. On the residency wording: Microsoft distinguishes **Data Zone**, which may process anywhere
  inside its zone (EU / US / APAC), from **GlobalStandard**, which may process in any Azure region
  ([deployment types](https://learn.microsoft.com/en-us/azure/foundry/foundry-models/concepts/deployment-types));
  `Decision-1` is the former and the narration model the latter, and wrapping Decision-1 in an agent changes
  neither its SKU nor its residency.
